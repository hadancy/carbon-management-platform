# 碳管理平台从零到一开发流程

> 文档状态：实施计划与开发进度（阶段 2、阶段 3 基础能力已落地）  
> 更新日期：2026-09-24  
> 目标读者：产品负责人、前端/全栈开发、碳核算业务人员、测试与运维  
> 项目位置：`Carbon-Management-Platform/`

## 1. 目标与边界

建设一套面向多所学校的碳管理平台。每所学校是独立租户，校内有多个使用者。首期业务界面只包含以下三个模块：

1. **碳足迹模型**：创建模型、定义生命周期阶段与数据项、维护因子、审核并发布模型版本。
2. **碳足迹核算**：选择已发布模型，录入活动数据，计算与复核各阶段排放量，形成可追溯的核算结果。
3. **碳足迹报告**：从已审核的核算结果生成报告，编辑说明文字、审核、预览和导出 PDF；可编辑 Word 作为后续需求。

登录、学校与账号管理、公共数据管理、权限、审计和文件存储是上述模块的基础能力。其中登录、学校与账号管理、公共数据版本、权限骨架和审计已实现；文件存储随业务模块建设。平台超级管理员在“学校与账号”工作区按学校管理成员或查看全部账号，另有公共数据与审计入口；学校用户的业务导航仍只展示上述三个模块。参考平台中的“碳模型”“产品碳排放”和模块管理等业务入口不进入新平台首期范围。

**首个交付闭环**：学校 A 的用户登录 → 建立并发布光伏模型 → 创建核算并录入活动数据 → 服务端计算并审核 → 生成、审核、下载 PDF 报告。随后用学校 B 重复流程并验证两校完全隔离。光热和风电在光伏闭环稳定后接入。

## 2. 首期技术方案

下表的 Web、界面、数据库、认证与参数校验方案已落地；数值运算、附件、PDF 和耗时任务是后续业务阶段的方案，尚未实现。

| 层次 | 选择 | 原因与边界 |
| --- | --- | --- |
| Web 与 API | Next.js App Router + TypeScript | 同仓库开发页面、服务端业务逻辑和 HTTP API；业务规则放在独立服务层，页面不直接写公式 |
| 后台界面 | Ant Design | 列表、复杂表单、步骤和审核状态较多，先保证录入效率与一致性 |
| 页面样式 | Ant Design 主题 Token + Tailwind CSS | 已用于后台布局与组件样式；不新增 CSS Modules，组件令牌由 `ConfigProvider` 管理 |
| 数据库 | PostgreSQL | 关系数据、事务和多租户约束；首期采用共享数据库、业务表按 `school_id` 隔离 |
| 数据访问 | Prisma | 类型化查询与数据库迁移；数据库约束仍需显式设计和验证 |
| 登录会话 | Better Auth | 已接入邮箱密码登录、会话与管理员操作；学校权限在本项目服务端校验，忘记密码由平台管理员重置 |
| 参数校验 | Zod | 管理接口已在服务端校验输入，后续业务接口沿用；不能依赖前端表单验证 |
| 数值运算 | 十进制 Decimal 库与数据库 `numeric` | 避免 JS 浮点误差；明确中间值与展示值的舍入规则 |
| 附件 | S3 兼容对象存储；本地开发可用 MinIO | 保存边界示意图、证据文件、导出的报告；文件元数据存数据库 |
| PDF | HTML 模板 + Playwright | 服务端按固定模板生成可复核的 PDF |
| 耗时任务 | 需要时增加队列与独立 Worker | 大批量计算或大量 PDF 导出时使用；Worker 仍可与 Next.js 共用 TypeScript 业务包 |

当前基础能力使用 Next.js 与 PostgreSQL；业务模块需要附件时再接入对象存储。若报告生成或导入任务出现明显超时，再增加队列与 Worker。生产环境应使用 Node 服务部署，不能使用只生成静态文件的模式承载 API。

## 3. 业务规则与待确认项（阶段 0）

下表保留首期决策及仍需确认的业务问题。已落地的学校和账号规则见[阶段 3 业务决策与权限](阶段3业务决策与权限.md)；其余规则在对应业务模块开发前由业务负责人确认。

| 问题 | 建议初始选择 | 需要确认的原因 |
| --- | --- | --- |
| 用户能否属于多所学校？ | 已实现多校归属；平台可按学校管理成员或查看全部账号，学校业务使用当前学校 | 账号与学校权限仍需分开校验 |
| 平台超级管理员做什么？ | 管理公共数据；创建、启停学校；创建、启停、删除非平台管理员账号，并维护归属和角色 | 已实现的首期能力；平台管理员账号不可删除 |
| 校内角色如何分工？ | 学校管理员、模型维护者、核算员、审核员、只读用户 | 影响每个 API 的权限与审核流 |
| 是否允许自己审核自己创建的内容？ | 默认不允许 | 影响模型、核算、报告的状态机 |
| 模型发布后能否编辑？ | 不直接编辑已发布版本；复制形成新版本 | 既有核算必须保持可复算 |
| 因子属于公共库还是学校私有？ | 公共基准因子由超级管理员维护；学校业务用户只读。是否允许学校私有因子另行确认 | 决定数据归属与来源记录 |
| 报告能否在核算变更后自动更新？ | 已审核报告固定快照；变更需新修订版 | 防止已导出报告与系统结果不一致 |
| 首期覆盖哪些产品？ | 先光伏，后光热、风电 | 控制公式实现与验收范围 |
| 报告导出格式？ | 首期 PDF；Word 如有明确用途再加入 | PDF 与真正的 `.docx` 是两套生成流程 |

**阶段产物**：业务决策记录、首期页面清单、角色权限矩阵、标准映射清单、一个经业务方手算确认的光伏样例。未确认的规则要标注“待确认”，不写成代码默认值。

### 3.1 已确定的两级管理范围

| 角色 | 可管理的对象 | 访问边界 |
| --- | --- | --- |
| 平台超级管理员 | 公共数据、学校组织、全平台账号、账号的学校归属和角色 | 公共数据独立于学校；管理账号不等于默认可查看学校私有模型、核算和报告 |
| 学校管理员 | 本校模型、核算和报告的规划管理动作；首期不管理账号 | 只能作用于所属学校 |
| 学校业务用户 | 根据校内角色处理模型、核算或报告 | 只能作用于所属学校 |

首期由超级管理员统一创建学校和账号；建校后界面引导创建首位学校管理员，也可将已有账号加入学校并设置角色。账号可跨校复用，移除某校归属不删除账号；删除非平台管理员账号则会撤销登录会话和凭据、移除全部归属，并保留匿名历史记录以维持审计及公共数据引用。超级管理员管理的公共数据现有三类版本化资料：排放因子、规则配置、通用报告模板；具体字段、数值和适用规则仍须经业务确认，当前尚不参与核算。发布新版本后，未来核算和报告应继续引用其使用时的旧版本快照。

### 4.1 核心数据表

下表同时列出已落地的基础表和后续业务表，状态以 2026-09-24 的代码与迁移为准。

| 表/实体 | 关键字段 | 说明 | 状态 |

| `FootprintReport` / `ReportRevision` | `schoolId`, `calculationRunId`, `templateVersion`, `status`, `contentSnapshot` | 报告版本与对应核算快照 | 规划 |

所有后续学校业务表都应带 `schoolId`；当前公共数据表不归属单个学校，由平台角色控制写入，学校用户只能读取已发布版本。除了全局唯一 ID，还要在关联写入时验证关联对象属于同一学校，或者是允许引用的公共数据；可用组合唯一约束与组合外键进一步防止跨校错误关联。删除已被核算引用的模型版本、因子版本或报告快照应受限制。

### 4.2 每次请求的租户上下文

1. 验证登录会话，得到可信的 `userId`。
2. 学校业务请求根据当前学校选择与 `SchoolMembership` 校验有效成员关系，得到可信的 `schoolId` 和校内角色；平台管理请求单独校验认证管理员角色与有效的 `PlatformRole`。
3. 在服务端数据访问层统一传入该上下文；列表、详情、更新、删除均按 `schoolId` 限定。
4. 对写入的关联 ID 再校验学校归属；禁止直接采用请求体里的 `schoolId` 决定数据归属。
5. 附件下载、报告导出、后台任务、缓存键和审计日志沿用同一 `schoolId`。

前端隐藏按钮只改善体验，不构成权限控制。学校 A 用户请求学校 B 的记录 ID 时，服务端必须拒绝或返回不泄露存在性的结果。数据库可补充 PostgreSQL 行级安全（RLS）作第二道防线，但需确认应用连接角色和事务上下文不会绕过策略。

**阶段验收**：两个学校可以使用相同的模型编码；任何学校业务记录均能追溯到 `schoolId`；学校 A 无法读取、修改、下载学校 B 的对象；普通学校用户不能修改公共数据或创建其他学校账号。

## 5. 分阶段实施流程

**截至 2026-09-24**：阶段 2 的项目骨架及阶段 3 的登录、学校与账号管理、公共数据版本、权限和审计基础能力已实现。已通过 `npm test`、`npm run typecheck`、`npm run lint`、webpack 生产构建及临时数据库集成测试。模型、核算、报告仍是占位页面；标准映射、核算样例和部分 M0 业务决策尚待确认。因此下文阶段 4 至阶段 9 仍是实施计划，不代表功能已经交付。

### 阶段 2：建立项目骨架与本地环境

**任务**

- 初始化 Next.js、TypeScript、Ant Design、Prisma 和 PostgreSQL；锁定依赖版本。
- 建立开发、测试、生产三套环境变量模板；真实密钥不入库。
- 建立数据库迁移、示例数据导入、格式检查、类型检查、构建命令。
- 建立登录页、三模块导航和统一空状态/错误页。
- 加入最小 CI：格式与静态检查、类型检查、关键单元测试、构建。
- 写 `README`：本地启动、数据库迁移、运行测试、部署所需变量。

**完成标准**：新同事按 README 在干净环境中启动应用；空数据库可通过迁移创建；CI 能发现构建失败。

### 阶段 3：平台管理、学校、用户、权限与审计

**已实现**

- 邮箱密码登录、登出、密码修改或重置后的会话失效，以及已授权学校之间的切换。
- 平台超级管理员创建、编辑和启停学校及账号；“学校与账号”工作区提供“按学校 / 全部账号”视图，可在学校内新建或添加已有账号、修改校内角色、移除单校归属，并在建校后引导创建首位学校管理员。
- 删除非平台管理员账号：服务端再次校验平台管理员权限并禁止删除平台管理员账号；删除时撤销会话和凭据、移除全部归属、匿名化保留历史记录，原邮箱可以重新使用。
- 公共数据草稿、编辑和版本发布；学校用户只读已发布版本。学校、账号、成员归属和公共数据操作写入审计日志。
- 已定义校内角色权限矩阵，并在现有管理 API 与学校上下文入口执行服务端权限和输入校验。临时数据库集成测试覆盖 A/B 学校、账号删除、归属移除、公共数据、会话失效与审计。

**后续阶段继续落实**：模型、核算、报告各 API 的角色与跨校检查，以及模型发布、因子修改、核算重算、审核和报告导出的审计；附件访问校验随文件存储落地。当前尚不能据此宣称业务模块或文件跨校隔离已完成验收。

### 阶段 4：碳足迹模型

**参考流程**：新建模型 → 模型列表 → 模型定义（阶段、类别、数据项）→ 提交审核 → 发布版本。

**任务**

- 实现模型基础字段：编码、名称、产品类型、功能单位、系统边界、边界示意图、引用标准、说明。
- 支持阶段、类别、数据项增删改与排序；每项记录活动数据单位、因子值、因子单位、来源、版本及有效期。
- 保存草稿、提交审核、驳回、发布；发布时验证必填项、单位匹配、因子来源和规则版本。
- 发布版本只读。修改时从已发布版本复制新草稿，已有核算继续引用旧版本。
- 先录入一个光伏模型与业务核对过的样例因子，不把原型的演示值直接当生产值。

**完成标准**：学校内模型编码唯一；发布前校验通过；发布后旧版本不可被悄然更改；跨校无法引用模型。

### 阶段 5：核算规则与计算引擎

**先形成标准映射表**，每条规则至少包含：标准编号与条款、产品类型、适用期间、输入变量、变量单位、取值来源、计算式、边界条件、舍入规则、示例及业务确认人。光伏、光热、风电分别维护规则映射；共用的运算工具与行业公式分开。

**实现顺序**

1. 定义带单位的输入类型与参数校验，拒绝缺失值、无效分母、非法百分比和不兼容单位。
2. 实现阶段排放计算和总碳足迹计算，采用十进制运算；中间值保留足够精度，只在规定节点舍入。
3. 用业务方提供的手算样例建立“固定输入 → 预期结果”的测试，不从旧 `app.js` 的输出反推预期值。
4. 记录规则版本、模型版本、因子版本、全部输入和分阶段结果，保存为 `CalculationRun` 快照。
5. 重算产生新的运行记录；审核通过的是特定运行记录，不能被后续编辑覆盖。

参考原型存在原材料、运输、设施建设、生产及退役、输配电和总上网电量等计算页面，但正式阶段划分、公式与参数必须以已确认的标准映射为准。

**完成标准**：同样的版本化输入产生相同结果；每个结果可追溯至因子和公式；零或非法分母给出明确错误；模型或因子更新不改变旧核算结果。

### 阶段 6：碳足迹核算页面与审核

**任务**

- 创建核算案例：产品、规格、计量单位、数据统计期间、学校、已发布模型版本。
- 按模型阶段录入活动数据，支持保存草稿、上传证据、显示数量与单位、标记缺失数据。
- 提供“计算”操作，展示分阶段结果、总结果、输入来源和计算警告。
- 提交审核、通过或驳回；驳回后修改并重算，再次提交。
- 编辑已审核案例时创建新修订，不覆盖原有计算运行记录。

**完成标准**：能用经确认的光伏样例从页面完成录入和核算；审核人能看到输入、计算结果与证据；跨校模型和因子不能混入核算。

### 阶段 7：碳足迹报告

**任务**

- 只有已审核的核算运行记录可创建待发布报告；报告绑定 `calculationRunId`。
- 按已确认的报告模板建立章节，自动带入产品、系统边界、阶段结果、总结果、因子来源与计算说明；人工说明可编辑。
- 报告正文与数值快照分离：人工编辑不能悄悄改写核算值。
- 实现草稿、提交审核、驳回、通过与修订；审核通过后冻结该修订版。
- 用同一份结构化报告数据生成页面预览与 PDF；校验页眉、分页、表格跨页、中文字体和附件权限。
- 文件下载经过服务端授权，或由服务端签发短时且限定对象的下载链接。

**完成标准**：PDF 中的数值与绑定的核算快照一致；修改核算后旧报告保持不变；学校 A 不能访问学校 B 的预览、文件或导出任务。

### 阶段 8：质量、安全与性能验证

**必测场景**

- **公式**：标准样例、边界值、单位换算、缺失/负数/零分母、重复计算、因子版本切换。
- **租户隔离**：A/B 同编码、列表、详情、更新、删除、关联 ID、附件、报告下载、后台任务和缓存；超级管理员的平台管理权限不得无意变成学校私有数据读取权限。
- **平台管理**：学校创建/停用、账号创建/停用/删除、学校归属添加/变更/移除、平台管理员删除保护、删除后的会话失效和邮箱复用、公共数据发布与旧版本引用；普通学校用户不能执行上述平台操作。
- **权限**：各角色逐项验证；审核状态不能跳级；不得越权自审（若业务决策采用该规则）。
- **一致性**：核算快照、报告快照、导出的 PDF 数值一致；失败的计算和导出可重试且不产生重复记录。
- **安全**：输入校验、文件类型与大小限制、对象存储私有访问、会话失效、审计日志、数据库备份与恢复演练。
- **性能**：按预估学校数、每校用户数、模型与案例数量做列表查询和导出压测；检查索引与数据库连接数。

**发布门槛**：CI 全绿；业务方签收至少一个光伏核算样例；A/B 跨校攻击用例全部通过；备份恢复和 PDF 样张检查通过。

### 阶段 9：预发布、上线与交接

1. 建立独立预发布环境，运行正式迁移与匿名化/演示样例导入。
2. 完成超级管理员、学校管理员、核算员、审核员的端到端验收；记录问题及修复版本。
3. 确认正式域名、证书、邮件或账户开通方式、数据库备份、对象存储、日志与告警。
4. 上线前备份数据库；执行迁移；发布应用；完成登录、核算、报告导出的烟雾测试。
5. 交付操作手册、角色权限矩阵、规则与因子版本清单、已知限制、回滚步骤。

**上线完成标准**：超级管理员可创建学校、账号并维护公共数据；至少两所真实或验收学校可独立完成流程；错误可定位到操作与版本；有可执行的备份恢复与回滚记录。

## 7. 开发中的关键约束

1. **租户隔离先于页面开发**：从第一张业务表和第一个 API 开始带学校上下文，避免后期补 `schoolId`。
2. **业务公式先于计算界面**：先有标准映射和可复核测试，再接入表单。
3. **版本与快照先于报告**：报告引用特定核算运行记录，保证对外结果稳定。
4. **来源先于默认值**：每个因子记录来源、适用时间、单位和版本；演示值不能无标记进入正式结果。
5. **权限在服务端生效**：学校和角色校验覆盖所有读取、写入、导出与任务执行路径。
6. **先跑通单产品闭环**：光伏端到端可验收后再增加光热、风电，减少规则与界面同时扩张。

## 9. 当前待确认清单

- 三份标准在项目计划上线时间的适用性、公式及报告模板采用方式。

这些问题不妨碍建立项目骨架和隔离架构，但在对应业务模块发布前必须形成书面决策。
