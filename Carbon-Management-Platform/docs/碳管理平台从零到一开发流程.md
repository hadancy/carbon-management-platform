# 碳管理平台从零到一开发流程

> 文档状态：实施计划与开发进度（阶段 2～7 与 M5 本机工程演练已通过；正式目标环境和业务签认待确认）
> 更新日期：2026-10-08\
> 目标读者：产品负责人、前端/全栈开发、碳核算业务人员、测试与运维  
> 项目位置：`Carbon-Management-Platform/`

## 1. 目标与边界

建设一套面向多所学校的碳管理平台。每所学校是独立租户，校内有多个使用者。首期业务界面只包含以下三个模块：

1. **碳足迹模型**：创建模型、定义生命周期阶段与数据项、维护因子、审核并发布模型版本。
2. **碳足迹核算**：选择已发布模型，录入活动数据，计算与复核各阶段排放量，形成可追溯的核算结果。
3. **碳足迹报告**：从已审核的核算结果生成报告，编辑说明文字、审核、预览和导出 PDF；可编辑 Word 作为后续需求。

登录、学校与账号管理、公共数据管理、权限、审计和文件存储是上述模块的基础能力。登录、学校与账号管理、公共数据版本、权限与审计已实现；碳足迹模型双轨发布、核算证据授权存储和报告 PDF 持久导出已接入。平台超级管理员在“学校与账号”工作区按学校管理成员或查看全部账号，另有公共数据、公用模型模板与审计入口；学校用户的业务导航仍只展示上述三个模块。参考平台中的“碳模型”“产品碳排放”和模块管理等独立业务入口不进入新平台首期范围。

**首个交付闭环**：学校 A 的用户登录 → 建立并发布通用碳足迹模型（首个核算样例可选光伏）→ 创建核算并录入活动数据 → 服务端计算并审核 → 生成、审核、下载 PDF 报告。随后用学校 B 重复流程并验证两校完全隔离。光热和风电的具体计算规则在首个闭环稳定后接入。

## 2. 首期技术方案

下表的 Web、界面、数据库、认证、参数校验、并网光伏纯数值内核和 PDF 方案已落地。核算证据与报告 PDF 首版存入数据库；对象存储和耗时任务队列按后续容量增加。模型示意图暂存于版本快照，大小与图片格式受限。

| 层次 | 选择 | 原因与边界 |
| --- | --- | --- |
| Web 与 API | Next.js App Router + TypeScript | 同仓库开发页面、服务端业务逻辑和 HTTP API；业务规则放在独立服务层，页面不直接写公式 |
| 后台界面 | Ant Design | 列表、复杂表单、步骤和审核状态较多，先保证录入效率与一致性 |
| 页面样式 | Ant Design 主题 Token + Tailwind CSS | 已用于后台布局与组件样式；不新增 CSS Modules，组件令牌由 `ConfigProvider` 管理 |
| 数据库 | PostgreSQL | 关系数据、事务和多租户约束；首期采用共享数据库、业务表按 `school_id` 隔离 |
| 数据访问 | Prisma | 类型化查询与数据库迁移；数据库约束仍需显式设计和验证 |
| 登录会话 | Better Auth | 已接入邮箱密码登录、会话与管理员操作；学校权限在本项目服务端校验，忘记密码由平台管理员重置 |
| 参数校验 | Zod | 管理接口已在服务端校验输入，后续业务接口沿用；不能依赖前端表单验证 |
| 数值运算 | 十进制 Decimal 库与数据库 `numeric` | 避免 JS 浮点误差；明确中间值与展示值的舍入规则 |
| 附件 | 首版数据库字节存储；后续迁移 S3 兼容对象存储 | 核算证据与报告 PDF 分开存储；按学校授权读取并验证摘要 |
| PDF | 共享 HTML 模板 + Playwright Chromium | 嵌入简体中文字体，按版本生成 A4 PDF；审核修订唯一持久导出 |
| 耗时任务 | 需要时增加队列与独立 Worker | 大批量计算或大量 PDF 导出时使用；Worker 仍可与 Next.js 共用 TypeScript 业务包 |

当前基础能力使用 Next.js 与 PostgreSQL；核算证据首版以限额 5 MB 的附件存入数据库，后续按容量迁移到对象存储。若报告生成或导入任务出现明显超时，再增加队列与 Worker。生产环境应使用 Node 服务部署，不能使用只生成静态文件的模式承载 API。

## 3. 业务规则与待确认项（阶段 0）

下表保留首期决策及仍需确认的业务问题。已落地的学校和账号规则见[阶段 3 业务决策与权限](阶段3业务决策与权限.md)。光伏业务待确认事项集中在[设计草案第 6 节](光伏核算规则映射与验算设计.md#6-业务决策登记)，约束对应方法的正式启用；通用能力及标明用途的试算可先开发。

| 问题 | 建议初始选择 | 需要确认的原因 |
| --- | --- | --- |
| 用户能否属于多所学校？ | 已实现多校归属；平台可按学校管理成员或查看全部账号，学校业务使用当前学校 | 账号与学校权限仍需分开校验 |
| 平台超级管理员做什么？ | 管理公共数据与公用模型模板；创建、启停学校；创建、启停、删除非平台管理员账号，并维护归属和角色 | 已实现的首期能力；平台管理员账号不可删除，也不默认查看学校私有模型 |
| 校内角色如何分工？ | 学校管理员、模型维护者、核算员、审核员、只读用户 | 影响每个 API 的权限与审核流 |
| 是否允许自己审核自己创建的内容？ | 默认不允许 | 影响模型、核算、报告的状态机 |
| 模型发布后能否编辑？ | 不直接编辑已发布版本；复制形成新版本 | 既有核算必须保持可复算 |
| 因子属于公共库还是学校私有？ | 首版复用平台公共因子版本，学校业务用户只读；学校私有因子作为后续独立扩展 | 首版的数据归属与引用关系可先确定，私有因子不作为开工依赖 |
| 报告能否在核算变更后自动更新？ | 已审核报告固定快照；变更需新修订版 | 防止已导出报告与系统结果不一致 |
| 首期覆盖哪些产品？ | 先光伏，后光热、风电 | 控制公式实现与验收范围 |
| 报告导出格式？ | 首期 PDF；Word 如有明确用途再加入 | PDF 与真正的 `.docx` 是两套生成流程 |

**阶段产物**：业务决策记录、首期页面清单、角色权限矩阵、标准映射清单、一个经业务方手算确认的光伏样例。当前[光伏规则映射与验算设计 v0.6](光伏核算规则映射与验算设计.md)已给出工程约定、合成验算数据、任务与完成证据；业务方法及真实样例尚待确认。未确认的参数不得成为正式业务默认值；工程测试可使用明确标记的合成数据。

### 3.1 已确定的两级管理范围

| 角色 | 可管理的对象 | 访问边界 |
| --- | --- | --- |
| 平台超级管理员 | 公共数据、公用模型模板、学校组织、全平台账号、账号的学校归属和角色 | 公用资料独立于学校；管理账号不等于默认可查看学校私有模型、核算和报告 |
| 学校管理员 | 本校模型、核算和报告的编辑、审核及导出；首期不管理账号 | 只能作用于所属学校；不能审核本人创建、最后编辑或提交的内容 |
| 学校业务用户 | 根据校内角色处理模型、核算或报告 | 只能作用于所属学校 |

首期由超级管理员统一创建学校和账号；建校后界面引导创建首位学校管理员，也可将已有账号加入学校并设置角色。账号可跨校复用，移除某校归属不删除账号；删除非平台管理员账号则会撤销登录会话和凭据、移除全部归属，并保留匿名历史记录以维持审计及公共数据引用。公共因子与规则配置已参与正式核算，并校验用途、期间及版本资格。公共报告模板仍是版本化资料，T07 使用受代码版本控制的内置工程模板；业务模板确认后通过受控映射接入。发布新版本不改写已有运行或报告快照。

### 4.2 每次请求的租户上下文

1. 验证登录会话，得到可信的 `userId`。
2. 学校业务请求根据当前学校选择与 `SchoolMembership` 校验有效成员关系，得到可信的 `schoolId` 和校内角色；平台管理请求单独校验认证管理员角色与有效的 `PlatformRole`。
3. 在服务端数据访问层统一传入该上下文；列表、详情、更新、删除均按 `schoolId` 限定。
4. 对写入的关联 ID 再校验学校归属；禁止直接采用请求体里的 `schoolId` 决定数据归属。
5. 附件下载、报告导出、后台任务、缓存键和审计日志沿用同一 `schoolId`。

前端隐藏按钮只改善体验，不构成权限控制。学校 A 用户请求学校 B 的记录 ID 时，服务端必须拒绝或返回不泄露存在性的结果。数据库可补充 PostgreSQL 行级安全（RLS）作第二道防线，但需确认应用连接角色和事务上下文不会绕过策略。

**阶段验收**：两个学校可以使用相同的模型编码；任何学校业务记录均能追溯到 `schoolId`；学校 A 无法读取、修改、下载学校 B 的对象；普通学校用户不能修改公共数据或创建其他学校账号。

### 阶段 2：建立项目骨架与本地环境

**任务**

- 初始化 Next.js、TypeScript、Ant Design、Prisma 和 PostgreSQL；锁定依赖版本。

- 加入最小 CI：格式与静态检查、类型检查、关键单元测试、构建。
- 写 `README`：本地启动、数据库迁移、运行测试、部署所需变量。

**完成标准**：新同事按 README 在干净环境中启动应用；空数据库可通过迁移创建；CI 能发现构建失败。

### 阶段 3：平台管理、学校、用户、权限与审计

**已实现**

- 邮箱密码登录、登出、密码修改或重置后的会话失效，以及已授权学校之间的切换。
- 平台超级管理员创建、编辑和启停学校及账号；“学校与账号”工作区提供“按学校 / 全部账号”视图，可在学校内新建或添加已有账号、修改校内角色、移除单校归属，并在建校后引导创建首位学校管理员。
- 删除非平台管理员账号：服务端再次校验平台管理员权限并禁止删除平台管理员账号；删除时撤销会话和凭据、移除全部归属、匿名化保留历史记录，原邮箱可以重新使用。
- 公共数据草稿、编辑和版本发布；学校用户只读已发布版本。学校、账号、成员归属和公共数据操作写入审计日志。
- 已定义校内角色权限矩阵，并在现有管理 API 与学校上下文入口执行服务端权限和输入校验。临时数据库集成测试覆盖 A/B 学校、账号删除、归属移除、公共数据、会话失效与审计。

**已延伸至模型、核算与报告**：各业务 API 已校验角色、学校、版本和状态；公共因子维护、核算重算、审核、报告导出与下载均记录审计。临时数据库集成测试覆盖跨校案例、附件、报告详情、预览和 PDF 隔离。部署配置、备份恢复及生产容量仍需在阶段 8～9 验证。

### 阶段 4：碳足迹模型

**当前流程**：平台管理员新建并发布公用模板；学校可从公用模板创建本校草稿，或自行新建模型 → 定义阶段、类别和数据项 → 提交校内审核 → 发布本校版本。

**任务**

- 已实现模型基础字段：编码、名称、功能单位数量、受控单位、功能说明、系统边界、边界示意图、引用标准、说明。
- 已实现用户自行增删改和排序阶段、类别、数据项；数据项保留原型中的名称、规格型号、生产厂家、原始碳足迹因子资料、活动数据单位、排放因子数值、因子来源和数据来源。因子版本、有效期和数值语义待规则映射确认后补充。
- 已实现草稿、提交校内审核、驳回、发布及基础完整性校验；模型与数据项发布前校验单位选项，排放因子单位由活动数据单位生成。活动数据与因子间的单位换算、因子引用、适用范围和规则版本校验仍待核算阶段落实。
- 已发布版本只读；修改从已发布版本复制新草稿，公用模板更新不改写学校版本。
- 删除草稿或被驳回的最新版本仅移除该版本，之前已发布版本继续可见；归档整个模型是单独操作，存在未发布版本时不能执行。
- 核算阶段再录入由业务方核对过的样例因子，不把原型演示值直接当生产值。

**完成标准**：学校内模型编码唯一；发布前校验通过；发布后旧版本不可被悄然更改；跨校无法引用模型。

### 阶段 5：核算规则与计算引擎

**先形成标准映射表**，每条规则至少包含：标准编号与条款、适用范围、适用期间、输入变量、变量单位、取值来源、计算式、边界条件、舍入规则、示例及业务确认人。光伏映射[已有待确认草案](光伏核算规则映射与验算设计.md)；各行业分别维护规则映射，共用的运算工具与行业公式分开。

**实现顺序**（对应草案 T01～T04）

1. 定义十进制字符串、单位和比例参数契约；因子复用公共数据版本，模型通过稳定 ID 映射计算角色。
2. 先完成并网场景、显式年度电量清单和有适用条件记录的输配电简化法；纯直供/混合供电保留独立分支，未启用时明确提示。
3. 用草案合成样例 `SYN-PV-001` 建立独立算术测试，再由业务方手算案例完成正式验收。业务确认与基础开发同步进行，不从旧 `app.js` 的结果反推预期值。
4. 接入案例修订、输入版本、幂等请求与不可变 `CalculationRun`；记录规则、引擎、模型、因子、单位换算、证据和完整过程。
5. 校验分场景分母、电量生命周期覆盖及估算年索引；重算产生新运行，提交必须对应当前输入。禁止误将纯直供的 `E_oge=0` 当作所有场景通用错误。

参考原型存在原材料、运输、设施建设、生产及退役、输配电和总上网电量等计算页面，但正式阶段划分、公式与参数必须以已确认的标准映射为准。

**完成标准**：同样的版本化输入产生相同结果；每个结果可追溯至因子和公式；当前场景必需分母非法时给出明确错误；模型或因子更新不改变旧核算结果。按用户指定范围，M3 已完成本轮构造案例流程验收；正式业务签认另行记录并用于对外启用。

### 阶段 6：碳足迹核算页面与审核

**任务**

- 创建核算案例及输入修订：产品、规格、计量单位、采集期间、生命周期、供电场景、学校、已发布模型及规则版本。
- 按模型阶段录入活动数据，支持保存草稿、上传证据、显示数量与单位、标记缺失数据。
- 提供“计算”操作，展示分阶段结果、总结果、输入来源和计算警告。
- 提交审核、通过或驳回；提交锁定当前输入和指定运行，服务端禁止创建人、最后编辑人及提交人自审。
- 驳回后或编辑已审核案例时创建新草稿修订，修改并重算；原输入、运行和审核记录均保留。

**完成标准**：能用经确认的光伏样例从页面完成录入和核算；审核人能看到输入、计算结果与证据；跨校模型和因子不能混入核算。

### 阶段 7：碳足迹报告

**已实现，T07 / M4 本轮演示验收完成**

- 只有已审核的核算运行记录可创建待发布报告；报告绑定 `calculationRunId`。
- 使用版本化内置工程模板，自动带入产品、系统边界、阶段结果、总结果、因子来源与计算说明；人工说明可编辑，业务模板确认后受控接入。
- 报告正文与数值快照分离：人工编辑不能悄悄改写核算值。
- 草稿允许未完成保存；提交前前后端检查必填说明并冻结正文摘要。独立复核人通过或驳回；新修订保留原版和意见，创建人、最后编辑人与提交人不能自审。
- 用同一份结构化报告数据生成页面预览与 PDF；校验页眉、分页、表格跨页、中文字体和附件权限。
- 通过审核的修订以唯一 `ReportExport` 保存 PDF；并发、重复导出复用同一文件。每次预览、生成和下载重新执行学校及角色授权，并校验冻结摘要和字节摘要。

**完成证据**：[T07 验收记录](T07报告验收记录.md) 与机器结果覆盖页面/PDF 数值一致、中文长文及表格跨页、修改核算后旧报告不变、禁止自审、篡改拦截、并发幂等和跨校下载隔离。已审核演示样张七页，逐页渲染检查通过。

### 阶段 8：质量、安全与性能验证

**必测场景**

- **公式**：标准样例、边界值、单位换算、缺失/负数/零分母、重复计算、因子版本切换。
- **租户隔离**：A/B 同编码、列表、详情、更新、删除、关联 ID、附件、报告下载、后台任务和缓存；超级管理员的平台管理权限不得无意变成学校私有数据读取权限。
- **平台管理**：学校创建/停用、账号创建/停用/删除、学校归属添加/变更/移除、平台管理员删除保护、删除后的会话失效和邮箱复用、公共数据发布与旧版本引用；普通学校用户不能执行上述平台操作。
- **权限**：各角色逐项验证；审核状态不能跳级；按已确定的禁止自审规则验证，学校管理员同样受约束。
- **一致性**：核算快照、报告快照、导出的 PDF 数值一致；失败的计算和导出可重试且不产生重复记录。
- **安全**：输入校验、文件类型与大小限制、对象存储私有访问、会话失效、审计日志、数据库备份与恢复演练。
- **性能**：按预估学校数、每校用户数、模型与案例数量做列表查询和导出压测；检查索引与数据库连接数。

**发布门槛**：CI 全绿；业务方签收至少一个光伏核算样例；A/B 跨校攻击用例全部通过；备份恢复和 PDF 样张检查通过。

## 7. 开发中的关键约束

1. **租户隔离先于页面开发**：从第一张业务表和第一个 API 开始带学校上下文，避免后期补 `schoolId`。
2. **公式与测试先于计算界面**：依据标准映射先实现可用合成数据验证的核心；业务样例约束正式启用，不阻塞通用基础开发。
3. **版本与快照先于报告**：报告引用特定核算运行记录，保证对外结果稳定。
4. **来源先于默认值**：每个因子记录来源、适用时间、单位和版本；演示值不能无标记进入正式结果。
5. **权限在服务端生效**：学校和角色校验覆盖所有读取、写入、导出与任务执行路径。
6. **先跑通单产品闭环**：光伏端到端可验收后再增加光热、风电，减少规则与界面同时扩张。
