# 部署与运维手册

更新时间：2026-10-08。适用范围为当前 Node 24、PostgreSQL、并网光伏及中文 PDF 版本。正式域名、主机规格、学校规模、责任人和备份保留策略尚待确定；本手册提供可执行步骤，不表示已经部署到生产环境。

## 1. 运行与容量配置

- 使用 Node 24，安装锁定依赖、生成 Prisma Client、构建生产包。PDF 需要 Chromium 及 `public/fonts/NotoSansSC-Regular.otf`；字体许可随项目提供。
- 通过密钥管理器注入 `.env.production.example` 中的 `DATABASE_URL`、HTTPS `BETTER_AUTH_URL` 和至少 32 字符的随机 `BETTER_AUTH_SECRET`。不使用示例值；同一发布和所有副本使用同一认证密钥。
- 每个 Node 进程默认 `DB_POOL_MAX=10`，连接等待 10 秒、空闲回收 30 秒。总连接预算为“副本数 × 池上限 + 迁移、备份、运维连接”，必须小于数据库 `max_connections` 并留余量。核算案例按学校和更新时间新增复合索引。
- `/api/health` 检查进程；`/api/ready` 检查数据库连接及本版本要求的报告列，未就绪返回 503。负载均衡使用就绪探针，故障监控结合进程、数据库和响应时间。
- 案例和报告列表当前在校内完整查询后分页显示，附件库显示最近 200 个文件。合成容量结果仅代表记录中的规模；规模扩大时先测实际响应体，再接服务端分页。证据单文件限额 5 MB，证据和 PDF 均在数据库，备份容量须包含这些字节。
- 新 PDF 渲染每进程最多同时执行 2 个任务；缓存文件下载并发不受该渲染上限影响。初次渲染负载与缓存下载须分别测量，不能用缓存压测替代首次导出容量验收。

## 2. 预发布与发布

1. 在独立预发布数据库运行迁移，使用合成数据验证全部角色和两校隔离。`npm run verify:release` 自动创建临时库、启动生产 Node 包、重跑完整业务与浏览器流程，并执行容量和备份恢复演练；结束清理数据库与服务。先构建，并准备 PostgreSQL、Chromium、Poppler、`pg_dump` 和 `pg_restore`。可通过 `PG_DUMP_BIN` / `PG_RESTORE_BIN` 指定工具路径。
2. 容量参数可设置 `LOAD_CASES`（默认 500，最多 10000）、`LOAD_CONCURRENCY`（20，最多 100）、`LOAD_REQUESTS`（200，最多 5000）。本机演练要求无失败、P95 小于 5 秒；正式 SLO 与规格按实际需求签认。
3. 构建不可变发布镜像：`docker build -t carbon-management:<发布编号> .`。`Dockerfile` 包含 Chromium、系统依赖和中文字体，运行用户为非 root。也可直接使用已测试的 Node 生产包。
4. 在部署主机设置 `APP_IMAGE` 为固定发布标签，按 `compose.production.yaml` 启动应用。外层反向代理负责实际域名、TLS 和访问日志；应用端口仅绑定主机回环地址。数据库由独立服务提供，生产 Compose 不创建或重置数据库。
5. 发布前保存当前镜像标签与数据库备份；执行 `npm run db:deploy`。迁移应由一个独立部署任务执行，不让多个副本竞争。然后运行 `npm run verify:deployment`，检查真实 HTTPS 域名、非占位密钥、数据库结构、字体及 Chromium。
6. 启动/切换应用，确认就绪、登录、切校、一次正式核算与独立审核、报告审核和 PDF 下载。记录应用版本、迁移版本和测试结果；观察错误率、P95、数据库连接及 PDF 延迟后开放流量。

本机生产 Node 包与独立库迁移已经验证。Docker Compose 语法验证通过；镜像构建尝试在拉取 Node 基础镜像时被本机 Docker DNS 故障阻断（`registry-1.docker.io` 解析失败），因此容器运行验收仍需在网络正常的部署主机执行。

## 3. 数据库备份与恢复

`npm run backup:db -- /私有备份目录/发布前.dump` 读取环境中的 `DATABASE_URL`，创建 PostgreSQL 自定义格式备份和同名 `.json` SHA-256 清单。目录须预先存在且仅运维账号可访问；文件权限为 0600，路径必须未被占用。密码只传工具环境变量，不放在命令行或输出中。备份包含所有业务记录、账号/会话、审计、附件和 PDF，应放在加密存储并按约定保留，不能保存到公开资料目录。

日常备份由部署平台的调度器调用同一命令，使用唯一时间戳文件名；确认退出码、文件大小及摘要清单，失败必须告警。备份频率、保留天数和 RPO/RTO 由实际业务规模确定。若要求低于一次全量备份间隔的 RPO，配置 PostgreSQL WAL 归档/PITR 并单独演练。

恢复时用密钥管理器设置 `RESTORE_DATABASE_URL`，目标数据库名称须为 `carbon_restore_...` 且不存在。运行 `npm run restore:db -- /私有备份目录/发布前.dump`：先验证清单与 SHA-256，再创建新库并恢复；不提供覆盖已有数据库的选项。运维恢复账号需有创建数据库权限。失败时保留新库用于排障，确认后清理，不能直接覆盖生产库。

恢复后执行正式迁移并检查学校、角色、案例修订、快照、审计、附件 SHA-256 和 PDF SHA-256；在独立应用实例完成登录、核算历史查看和下载验证，再决定是否切换连接。恢复连接切换需要业务确认可接受的恢复时间点。

自动演练复用上述备份/恢复实现，将合成数据恢复到独立新库，对所有表按排序后的行内容核对数量和 SHA-256（包括二进制附件与 PDF），并验证迁移可重复执行。演练后删除备份和临时库；正式备份由运维保留。

## 4. 回滚

本次迁移只增加可空 `templateSnapshot` 和案例索引，旧报告摘要与旧模板保留兼容。应用故障时将 `APP_IMAGE` 改回上一个固定标签并重新启动，优先保留这些新增列和索引，不执行数据回退或删除历史报告。

如果需要回滚数据库或未来出现破坏性迁移，先停止写入并保留当前库、日志与备份，再按“恢复到独立新库”的步骤演练和核对。不得直接在生产执行 `migrate reset`、删除迁移记录或覆盖现有库。切换前记录恢复点与会丢失的后续写入，并由实际业务负责人确认。

## 5. 日志、告警与交接

API 未知错误与就绪/PDF 故障输出 JSON 日志：时间、事件、错误类型/代码与请求编号。500 响应和失败就绪响应附带请求编号，便于关联；不输出密码、Cookie、连接串或完整表单。反向代理记录请求编号、路由、HTTP 状态与耗时，排除敏感认证参数。Compose 为日志配置 10 MB × 5 的轮转，正式环境汇聚到已有日志服务。

告警至少接入：持续未就绪、HTTP 5xx 增长、连接耗尽/连接等待超时、磁盘/数据库容量、备份任务失败、恢复演练失败、PDF 渲染失败/繁忙增长。阈值和通知渠道由运维确定；本项目没有在未知渠道上创建实际通知。

学校操作顺序：管理员配置并发布完整规则与因子 → 模型维护者录入并提交 → 独立审核员发布本校模型 → 核算员新建案例、逐项录入、年度生成/CSV 导入及证据复用 → 保存草稿、试算、正式计算、提交 → 独立审核员通过或驳回 → 通过后选择内置或已发布公共报告模板生成报告 → 填写日期、说明与结论，提交独立审核 → 通过后预览和导出。输入变化须重算，通过/驳回后创建新修订；旧快照、旧模板和旧 PDF 保持固定。

交接时确认正式域名/证书、部署目标与容量、密钥/备份管理权限、平台首位管理员、学校开户方式、日志告警责任人，以及 B01～B06 方法、正式因子、真实手算案例与报告模板签认。相关工程证据见 [全流程修复验收](2026-10-08全流程修复验收.md)。
