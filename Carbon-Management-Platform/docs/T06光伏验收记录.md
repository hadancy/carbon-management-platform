## 3. 可执行验收包

`tests/fixtures/pv-acceptance-reference.json` 为 `STD-PV-REF-001`。因子有一手来源，活动量、寿命、年度电量和 5% 线损是构造输入，不代表实际电站，不覆盖真实项目全部设备。`caseKind=PUBLIC_REFERENCE`，因子与规则 `purpose=TEST`，签认字段保持待填写。

[独立算术说明](acceptance/pv-reference-handcalc.md)使用 Python 标准库 Decimal 80 位精度，没有调用应用内核或原型。27 项比对覆盖逐项归一活动量和排放、五阶段、总量、上网/交付电量及展示值。预期为 `3688.9 kgCO2e / 95000 kWh`，展示碳足迹 `0.038831 kgCO2e/kWh`。

```bash
npm run verify:pv
npm run verify:pv -- /实际位置/验收包.json --output /实际位置/新结果.json
npm run verify:pv -- /实际位置/验收包.json --require-business
```

第三条是后续正式业务资料检查，资料缺失时返回非零退出码。离线工具的 `PENDING_BUSINESS` 表示数值通过但正式资料不足，不影响本轮 `DEMO_WORKFLOW / PASSED`；`FAILED/INVALID` 表示输入、数值或已保存运行不一致；`READY_FOR_REVIEW` 表示正式资料满足完整性检查。

命令不连接数据库、不上传附件、不发布生产数据。结果包含验收包、范围、源码与锁文件的 SHA-256、逐项比较和缺口；新结果文件拒绝覆盖来源或已有结果。

### 后续正式业务案例接入步骤

1. 另存案例包，使用实际学校和案例 ID。在已授权会话读取 `/api/accounting/runs/{id}`，复制 `run` 和 `run.snapshots`；不要从现行因子库重建历史快照。
2. 由独立手算或外部工具填写逐项与汇总预期，提供原始证据，不从应用结果反填。只有 BUSINESS 包能进入业务资料就绪检查，改变标记本身不构成验收。
3. 在 `evidence` 登记来源相对路径与 SHA-256；运行附件同时核对实际字节数。补齐项目、活动、年度电量凭证和方法依据。
4. 执行命令取得 `scopeHash`。B01～B06、签认和三项流程证据须绑定该范围，确认人、日期、结论及证据由实际责任人填写。输入、模型、规则、因子、独立预期或运行变化后重新确认范围。
5. 补入审核修订、两校隔离、旧结果冻结的流程证据，执行 `--require-business`；实际责任人核对签认后发布对应正式业务配置。本轮 M3c 的演示流程完成状态独立保留。

独立预期文件和运行附件摘要绑定范围；签认文件在范围外单独检查，避免签认文件内的范围摘要造成循环引用。
